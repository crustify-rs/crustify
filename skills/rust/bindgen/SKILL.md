# Raw bindings

How a campaign's raw bindings are laid out, generated, built and shipped. They are
generated by bindgen from the C under `c/`, one module per link unit, and ship inside the
safe crate as its public `ffi` module, with the C they bind: the published crate carries
the generated bindings, so that a dependent builds without bindgen or libclang, and the C
that remains, so that a dependent has the whole library and reaches what is not
translated yet through the raw bindings. How the safe crate uses them is
[`binding`](../binding/SKILL.md)'s; their lints and formatting are
[`toolchain`](../toolchain/SKILL.md)'s Generated code section's.

## 1. Layout

```text
<repository>/
├── Cargo.toml            the safe crate's manifest; bindgen an optional build dependency
├── build.rs              builds or locates the C, compiles the C wrappers, regenerates on request
├── c/                    the C that remains, built into the crate
├── ffi/<link-unit>/      one link unit's bindings
│   ├── wrapper.h         the headers they cover: the installed headers, and the internal headers its batches bind items of
│   ├── allowlist.txt     one `function|type|var <regex>` per line, filled by the batches
│   ├── external.txt      the types other link units' bindings own, one regex per line
│   ├── shims.h
│   ├── shims.c           the `crustify_<NAME>` macro shims
│   ├── bindings.rs       generated, committed
│   └── static_fns.c      generated wrappers of the allowlisted `static inline` functions, committed
└── src/ffi.rs            the `ffi` module: one public module per link unit, including its committed or regenerated bindings
```

Everything a build reads sits inside the crate, so that the packaged crate builds on its
own: no path leaves it, and `crustify/` is read only in campaign mode.

Within a link unit's Rust, `crate::ffi::<link_unit>` is imported as `ffi`, so that a raw
binding is `ffi::<name>`, as the [conventions](../conventions/SKILL.md)' Naming section spells it.
The `ffi` module is public: a consumer reaches the C that is not translated yet through
it, under its C names.

`c/` is the C that remains: in a wrap campaign the whole source, and in a port campaign
the fork's `main`, which each switch trims of the module it ports, as
[`porting-workflow`](../../workflows/porting-workflow/SKILL.md)'s Builds section describes. A build of
the crate therefore never holds both a module's C and the Rust that replaces it: the
remaining C reaches a ported module through the safe crate's exports, under their bare C
names, as the conventions' Exports section describes.

## 2. Generation

The bindings follow from the headers at the `c/` revision, the allowlists, the generator
settings below and the bindgen version, pinned exactly in `Cargo.toml`, so that generating
twice from the same input gives the same bytes. The settings are the same for every
campaign:

- the output is formatted by bindgen's own formatter (`prettyplease`), never by the
  toolchain's `rustfmt`, whose output differs between toolchains, so that a nightly build
  regenerates the bytes a stable one committed;
- enums are generated as constants (`Consts`), without the enum name as a prefix, which
  the safe types that bind them convert, as [`binding-types`](../binding/types/SKILL.md)'s Enums
  section describes;
- `Default` is derived, and layout tests are generated;
- C comments are kept as doc comments, and the generated modules' doctests are off, since
  they hold C;
- each allowlisted `static inline` function gets a compiled wrapper, `<name>__extern`, in
  `static_fns.c`, and is bound under its own name through
  `#[link_name = "<name>__extern"]`, so that it is called as an exported function is:
  bindgen's `wrap_static_fns`;
- macro shims are bound like the functions they wrap; and
- an empty allowlist generates nothing.

A type that another link unit's bindings own is blocklisted, as `external.txt` lists it,
and re-exported from that link unit's module under its C name, so that each C type has one
Rust type across the crate. A type an out-of-tree library's wrapper publishes is
re-exported as its wrapper's safe type, as
[`dependencies`](../../planning/dependencies/SKILL.md)'s Routes section describes.

The bindings are generated for the campaign's target, the host's, as the setup workflow's
Builds section names it, the only target the crate supports: `src/ffi.rs` fails to compile
on any other, naming it.

The C an out-of-tree library's wrapper bundles once its side campaign has ported part of
the library is compiled with its symbols prefixed, as
[`dependencies`](../../planning/dependencies/SKILL.md)'s Side campaigns section asks:
a generated header, force-included in every compile of that C and of its shims and
wrappers, renames each global symbol the library defines to `crustify_<library>_<name>`,
and bindgen binds each item under its C name with the prefixed symbol as its `link_name`,
so that the Rust names stay C's. The crate passes the header's path to the C builds of the
crates that depend on it through its build script's metadata, under its `links` key, and
those force-include it too, so that their C calls the same copy.

## 3. Build modes

The build script runs in one of four modes:

| mode | when | C |
|---|---|---|
| bundled | by default, but for a wrapper whose `c/` is still its whole library | `c/`, built statically into `OUT_DIR` by the target's own build system, in the configuration of the `plain` variant |
| shared | the `shared` feature | `c/`, built as shared libraries into `OUT_DIR`, the same way |
| system | the `system` feature, and by default for a wrapper whose `c/` is still its whole library | an install, found through `<LIB>_DIR`, then `pkg-config` |
| campaign | `CRUSTIFY_BUILD_VARIANT` names a variant, or `CRUSTIFY_BUILD_DIR` a private build | the variant's build, recorded in `crustify/artifacts/build.json`: its static archive, when it records one, else its shared libraries |

The campaign's repository sets `CRUSTIFY_BUILD_VARIANT` to `plain` in its
`.cargo/config.toml`, so that every build there runs in campaign mode unless the variable
names another variant, or is set empty to build as a dependent would.

In every mode, `shims.c` and `static_fns.c` are compiled against the headers the bindings
match, with the instrumentation of the C they link, and the bindings are the committed
ones unless the `bindgen` feature regenerates them into `OUT_DIR` from the headers of that
C. Campaign mode's tests and gates always regenerate them.

Bundled mode links the C statically, so that the bindings and the C they call always come
from the same revision; it sets no rpath. Shared mode leaves the remaining C's references
to ported modules undefined in its shared libraries, and the build script has the final
binary export what resolves them (`-Wl,--export-dynamic-symbol=<name>` for each export),
as a cdylib already does; the libraries are found beside the binary, through an `$ORIGIN`
rpath, and ship with it.

System mode serves a crate whose `c/` is still the whole source: once a port campaign has
switched a module, an install of the library would hold that module's C beside the Rust
that replaces it, and the build fails, naming the switched modules. It checks the
version: the library found must be the one the bindings were generated from, as its build
system reports it (`pkg-config --modversion`), or, for an out-of-tree library's wrapper, a
release ABI-compatible with it, which shares its soname. Another version fails the build
with both versions named, unless the `bindgen` feature regenerates the bindings for it. Each link
unit's module exports the version the bindings match as `C_VERSION`. `<LIB>_DIR` names an
install prefix: the build reads the headers under its `include/`, links the library under
its `lib/`, and takes the version from `lib/pkgconfig/<lib>.pc`. Without it, `pkg-config`
finds the library, which is linked as `pkg-config` resolves it, with no rpath.

Campaign mode serves the campaign while it extends the bindings: batches add allowlist
entries and shims, and the bindings follow from them. It needs bindgen, which the safe
crate enables for its own tests through a dev-dependency on itself with the `bindgen`
feature, so that the campaign's tests and gates regenerate while dependents build from
the committed bindings. A build that does not enable the feature, such as the crate's
documentation, uses the committed bindings unchecked; the tests and gates always enable it.
The bindings it generates are compared with the committed ones: a difference fails the
build, naming the regenerated file, unless `CRUSTIFY_BINDINGS_UPDATE` is set, in which case
they are written over `bindings.rs` and `static_fns.c`. It links the C the variant built,
so that every test runs against the instrumented C it was built for. A variant that
records a `static` archive, as [`setup`](../../workflows/setup/SKILL.md)'s Builds section
describes, has it linked statically, with the libraries its shared library links, so that
the Rust reaches the internal functions the shared library does not export, and the
remaining C resolves the exports within the same link, as bundled mode's does; only the
out-of-tree libraries' installs of the same variant take an rpath. A variant that records
none has its shared libraries linked with an rpath to them, and the test binaries export
what the remaining C resolves to, as shared mode does.

No build links two copies of a module: a mode links either a module's C or the Rust that
replaces it, never both, and the Rust static library that the target's remaining C links
from a module's switch on carries no C of its own, as the porting workflow's Builds
section describes.

## 4. Extending

The bindings grow with the batches: a batch whose items need a raw binding the bindings
lack extends its own link unit's input, and nothing else:

1. its link unit's `allowlist.txt` gains only the FFI items its items need, and
   `wrapper.h` an internal header only when one of them is declared there;
2. a shim is added to `shims.h` and `shims.c` only for a macro whose expansion depends on
   the build's configuration, as `crustify_<NAME>`, as
   [`binding-symbols`](../binding/symbols/SKILL.md)'s Macros section describes;
3. the bindings are regenerated, in campaign mode with `CRUSTIFY_BINDINGS_UPDATE` set; and
4. the safe crate is built and tested against them.

An allowlist or `wrapper.h` change alone leaves the C library as it is, so it reuses a
prebuilt variant; a shim compiles with the crate, as [Build modes](#3-build-modes) describes.

## 5. Landing

A batch that changes an allowlist, `external.txt`, a shim or `wrapper.h` regenerates the
bindings and commits them in the same landing, so that the committed bindings always match
their input. The gates that check it, and that the crate packages, are
[`testing-gates`](../../verification/testing/gates/SKILL.md)'s Regressions section's.

## 6. Publishing

The safe crate is published with its raw bindings and the C it bundles. The packaged crate
holds the layout above, `src/` and the files of `c/` that the bundled build reads, and
nothing else of the repository.
