# Raw bindings

How a port's raw bindings are laid out, generated, built and extended. The port reaches
the C that stays in the build through them: the components not ported yet, the
platform-specific branches kept in C and the libraries the target uses from outside. They
are generated by bindgen from the C's headers, one module per link unit, and ship inside the
safe crate as its public `sys` module. Their lints and formatting are
[`toolchain`](../toolchain/SKILL.md)'s Generated code section's.

## 1. Layout

```text
<crate>/
├── Cargo.toml            the safe crate's manifest; bindgen an optional build dependency
├── build.rs              locates or builds the C, compiles the C wrappers, regenerates on request
├── sys/<link-unit>/      one link unit's bindings
│   ├── wrapper.h         the headers they cover: the installed headers, and the internal headers the port reaches items of
│   ├── allowlist.txt     one `function|type|var <regex>` per line
│   ├── external.txt      the types other link units' bindings own, one regex per line
│   ├── shims.h
│   ├── shims.c           the `crustify_<NAME>` macro shims
│   ├── bindings.rs       generated, committed
│   └── static_fns.c      generated wrappers of the allowlisted `static inline` functions, committed
└── src/sys.rs            the `sys` module: one public module per link unit, including its committed or regenerated bindings, or their doctest copy, and the re-exports of the types other link units own
```

Within a link unit's Rust, `crate::sys::<link_unit>` is imported as `sys`, so that a raw
binding is `sys::<name>`, as the [conventions](../conventions/SKILL.md)' Naming section spells it.
The `sys` module is public: a consumer reaches the C that is not translated yet through
it, under its C names. It takes the place of the ecosystem's `-sys` crates, and is named after them.

## 2. Generation

The bindings follow from the headers, the allowlists, the generator settings below, the
bindgen version, pinned exactly in `Cargo.toml`, and the LLVM pinned below, so that
generating twice from the same input gives the same bytes. The settings are:

- the output is formatted by bindgen's own formatter (`prettyplease`), never by the
  toolchain's `rustfmt`, whose output differs between toolchains, so that a nightly build
  regenerates the bytes a stable one committed;
- enums are generated as constants (`Consts`), without the enum name as a prefix, which
  the safe types over them convert;
- `Default` is derived, and layout tests are generated;
- C comments are kept as doc comments, and no doctest is collected from them, since they
  hold C: the generated modules are modules of the safe crate, which rustdoc cannot exempt
  one by one, so its doctests are collected from a copy of whichever bindings the build
  uses, committed or regenerated, whose C comments are plain comments: the build script
  writes it into `OUT_DIR`, and `src/sys.rs` includes it in their place under
  `cfg(doctest)`;
- each allowlisted `static inline` function gets a compiled wrapper, `<name>__extern`, in
  `static_fns.c`, and is bound under its own name through
  `#[link_name = "<name>__extern"]`, so that it is called as an exported function is:
  bindgen's `wrap_static_fns`;
- macro shims are bound like the functions they wrap; and
- an empty allowlist generates no item: `bindings.rs` holds only bindgen's banner, and
  `static_fns.c` stays, empty, so that every link unit has both generated files.

An internal header's declarations are generated, and the wrappers of its `static inline`
functions compiled, as the link unit's own translation units see them: with the include
dirs and preprocessor definitions the target's build records for them, its generated
headers and its out-of-tree libraries' include dirs among them. An item whose declaration
depends on a definition that differs between the sanitizer and plain builds is generated
from the plain build's configuration, so that the committed bindings serve every build.

A type that another link unit's bindings own is blocklisted, as `external.txt` lists it,
and re-exported from that link unit's module under its C name, so that each C type has one
Rust type across the crate. A type a dependency's crate already defines, as `crustify/DEPS.md`
records the dependency, is re-exported from that crate rather than generated again.

The bindings are generated for the host's target, the only one the port builds and tests
on: `src/sys.rs` fails to compile on any other, naming it, until the C of that platform is
bound too.

The LLVM that generates the bindings, its libclang and the clang bindgen asks for the
system include dirs, is pinned with the bindgen version: its install prefix and version, in
the workspace manifest's `[workspace.metadata.crustify]`, as `bindgen-llvm` and
`bindgen-llvm-version`. Generation uses it whatever drives the build, a sanitizer's or
Miri's cargo driver included, which may name another libclang of its own, and fails,
naming both versions, when the pinned one is missing or reports another version.

## 3. Building

The crate links the C that the target's own build system builds, in the configuration the
build needs, plain or instrumented, so that every test runs against the C it was built for.
`shims.c` and `static_fns.c` are compiled against the headers the bindings match, with the
instrumentation of the C they link.

The bindings are the committed ones unless the `bindgen` feature regenerates them into
`OUT_DIR`. The crate's own tests and gates enable it, through a dev-dependency on itself
with the feature, and compare the regenerated bindings with the committed ones: a
difference fails the build, naming the regenerated file, unless `CRUSTIFY_BINDINGS_UPDATE`
is set, in which case they are written over `bindings.rs` and `static_fns.c`. A build that
does not enable the feature, such as the crate's documentation, uses the committed bindings
unchecked.

Linking the C statically keeps the bindings and the C they call at the same revision, and
reaches the internal functions a shared library does not export; the remaining C resolves
the Rust exports within the same link. Where the C is linked as shared libraries instead,
the remaining C's references to ported modules stay undefined in them, and the final binary
exports what resolves them (`-Wl,--export-dynamic-symbol=<name>` for each export), as a
cdylib already does.

No build links two copies of a component: it links either the component's C or the Rust
that replaces it, never both, and the Rust static library the remaining C links carries no
C of its own.

A link unit the target links as an executable, such as a command-line tool, has no
library: its translation units are compiled as the target's build system records them,
without linking the executable, and their objects archived. An archive member is linked
only where one of its symbols is referenced, so a test that references the translation unit
defining the executable's `main`, directly or through another member that references it,
links a second `main` beside its harness's and fails to link. That unit's other symbols are
therefore ported to exports first, so that the members which reference them stop pulling it
in, and until then the units that pull it in are tested through the executable, run as a
child process.

## 4. Extending

The bindings grow with the port: a component that needs a raw binding the bindings lack
extends its own link unit's input, and nothing else:

1. its link unit's `allowlist.txt` gains only the FFI items the component needs, and
   `wrapper.h` an internal header only when one of them is declared there;
2. a shim is added to `shims.h` and `shims.c` only for a macro whose expansion depends on
   the build's configuration, as `crustify_<NAME>`;
3. the bindings are regenerated with `CRUSTIFY_BINDINGS_UPDATE` set; and
4. the safe crate is built and tested against them.

Where its link unit's headers name a type another link unit owns, the component also
extends what the re-export needs, and only that: the type joins its own link unit's
`external.txt`, the owning link unit's `allowlist.txt` too while its bindings lack the type,
and the link unit's module in `src/sys.rs` re-exports it from the owner's, under its C name.

A change to an allowlist, `external.txt`, a shim or `wrapper.h` regenerates the bindings
and commits them in the same commit, so that the committed bindings always match their
input. The gates that check it are [`testing-gates`](../../verification/testing/gates/SKILL.md)'s.

The bindings shrink with the port too: a raw binding goes once nothing in the crate calls
it, with the allowlist entry, shim or `wrapper.h` header that produced it.
