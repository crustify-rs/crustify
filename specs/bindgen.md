# Raw bindings

How a campaign's `-sys` crates are laid out, generated, built and shipped. Each holds one
link unit's raw bindings, generated by bindgen from the C under `c/`, and ships with the
safe crate: its generated bindings are published with it, so that a dependent builds
without bindgen or libclang, and its build script regenerates them on request against the
headers a dependent builds with. How the safe crate uses them is
[`items/binding.md`](items/binding.md)'s; their lints and formatting are
[`rust.md`](rust.md)'s Generated code section's.

## 1. Crate layout

```text
<link-unit>-sys/
├── Cargo.toml            `links` names the library; bindgen an optional build dependency
├── build.rs              locates the library, compiles the C wrappers, regenerates on request
├── bindgen/              the generator's input
│   ├── wrapper.h         the public headers the link unit installs
│   ├── allowlist.txt     one `function|type|var <regex>` per line, filled by the batches
│   ├── external.txt      the types other crates own, one regex per line
│   ├── shims.h
│   └── shims.c           the `crustify_<NAME>` macro shims
└── src/
    ├── lib.rs            the crate root, including the shipped or the regenerated bindings
    ├── bindings.rs       generated, committed
    └── static_fns.c      generated wrappers of the allowlisted `static inline` functions, committed
```

Everything a build reads sits inside the crate, so that the packaged crate builds on its
own: no path leaves it, and neither `c/` nor `crustify/` is read outside campaign mode.

Each crate's `build.rs` is a copy of one build script, which differs between crates only
in a block of constants at its top: the library's name, its `pkg-config` module, the
version the bindings were generated from, and the link units it depends on. A change to
the script is made in every copy at once.

## 2. Generation

The bindings follow from the headers at the `c/` revision, the allowlists, the generator
settings below and the bindgen version, pinned exactly in each `Cargo.toml`, so that
generating twice from the same input gives the same bytes. The settings are the same for
every campaign:

- the output is formatted by bindgen's own formatter (`prettyplease`), never by the
  toolchain's `rustfmt`, whose output differs between toolchains, so that a nightly build
  regenerates the bytes a stable one committed;
- enums are generated as constants (`Consts`), without the enum name as a prefix, and
  used directly, as `items/binding.md`'s Type route section describes;
- `Default` is derived, and layout tests are generated;
- C comments are kept as doc comments, and the crate's doctests are off, since they hold
  C;
- each allowlisted `static inline` function gets a compiled wrapper, in `static_fns.c`;
- macro shims are bound like the functions they wrap; and
- an empty allowlist generates nothing.

A type that another link unit's crate, or an out-of-tree library's wrapper, publishes is
blocklisted, as `external.txt` lists it or as the dependency's crate defines it, and
re-exported from that crate under its C name, so that each C type has one Rust type
across the graph. An out-of-tree type is re-exported as its wrapper's safe type, as
[`dependencies.md`](dependencies.md)'s Wrappers section describes.

The bindings are generated for `x86_64-unknown-linux-gnu`, the only target the crates
support: `lib.rs` fails to compile on any other, naming the target.

## 3. Build modes

The build script runs in one of three modes:

| mode | when | bindings | C library |
|---|---|---|---|
| shipped | by default | `src/bindings.rs` | an install, found through `<LIB>_DIR`, then `pkg-config` |
| regenerate | the `bindgen` feature | generated into `OUT_DIR` from the headers found | as shipped |
| campaign | `CRUSTIFY_BUILD_VARIANT` names a variant, or `CRUSTIFY_BUILD_DIR` a private build | generated into `OUT_DIR` from `c/` and the variant | the variant's build, recorded in `crustify/artifacts/build.json` |

The campaign's repository sets `CRUSTIFY_BUILD_VARIANT` to `plain` in its
`.cargo/config.toml`, so that every build there runs in campaign mode unless the variable
names another variant, or is set empty to build as a dependent would.

In every mode, `shims.c` and `static_fns.c` are compiled against the headers the bindings
match, with the instrumentation of the library they link.

Shipped mode checks the version: the library found must be the one the bindings were
generated from, as its build system reports it (`pkg-config --modversion`). Another
version fails the build with both versions named, unless the `bindgen` feature
regenerates the bindings for it. `lib.rs` exports the version the bindings match as
`C_VERSION`. Shipped and regenerate modes link the library as `pkg-config` resolves it,
and set no rpath.

`<LIB>_DIR` names an install prefix: the build reads the headers under its `include/`,
links the library under its `lib/`, and takes the version from `lib/pkgconfig/<lib>.pc`.
Without it, `pkg-config` finds the library.

Campaign mode serves the campaign while it extends the bindings: batches add allowlist
entries and shims, and the bindings follow from them. It needs bindgen, which the safe
crate's dev-dependencies enable through each `-sys` crate's `bindgen` feature, so that the
campaign's tests and gates regenerate while the crate's dependents build from the shipped
bindings. A build that does not enable the feature, such as the documentation of the safe
crate alone, uses the committed bindings unchecked; the tests and gates always enable it.
The bindings it generates are compared with the committed ones: a difference
fails the build, naming the regenerated file, unless `CRUSTIFY_BINDINGS_UPDATE` is set, in
which case they are written over `src/bindings.rs` and `src/static_fns.c`. It links the
variant's build with an rpath to it, so that every test runs against the instrumented
library it was built for.

## 4. Landing

A batch that changes an allowlist, `external.txt`, a shim or `wrapper.h` regenerates the
bindings and commits them in the same landing, so that the committed bindings always match
their input. The gates that check it, and that each crate packages, are
[`testing.md`](testing.md)'s Regressions section's.

## 5. Publishing

The `-sys` crates are published before the safe crate, in the order of their link units'
dependencies, each at the safe crate's version. The packaged crate holds its layout above
and nothing else of the repository.
